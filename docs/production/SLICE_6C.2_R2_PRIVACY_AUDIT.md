# Slice 6C.2: R2 Privacy Model + Staging Readiness Final Audit

## 1. Executive Summary

This slice resolves the final architectural ambiguity regarding the privacy model of image previews and completes the staging-readiness audit. The system now guarantees that all customer-derived data (both original uploads and generated previews) is strictly isolated in private storage, while product catalogue imagery remains securely routed to a public CDN edge.

**Result:** `READY FOR STAGING INFRASTRUCTURE`

## 2. Critical R2 Privacy Audit

### 2.1 The Previews Ambiguity
In Slice 6C.1, `previews/*` were tentatively mapped to the `R2_PUBLIC_BUCKET_NAME`. A deeper audit of `apps/api/src/controllers/storage.controller.ts` (`uploadComplete`) conclusively verified that `previews/*` are generated by `sharp` down-sampling raw customer uploads (`customers/*`). 

**Conclusion:** Previews are customer-derived proxies. Exposing them in a public bucket with easily guessable UUIDs violates the strict zero-public-access policy for customer data.

### 2.2 Architectural Correction
We have re-architected the storage provider:
- **PRIVATE Bucket:** `customers/*` (original uploads) and `previews/*` (generated proxies).
- **PUBLIC Bucket:** `products/*` (catalogue assets).

The API now exposes a secure redirection endpoint (`GET /api/v1/storage/preview/:file_key`) that verifies session/user ownership and issues an ephemeral (1-hour) HTTP 302 redirect to a presigned R2 URL, allowing frontend `<img src="...">` tags to securely render private previews without breaking caching or requiring custom fetch mechanisms.

## 3. Legacy `weprintit-assets` Bucket Audit

A live audit of the existing `weprintit-assets` bucket confirmed:
- **Total Objects:** 123 (56 `customers/`, 56 `previews/`, 11 `products/`).
- **Total Size:** ~7.43 MB.
- **Nature of Data:** All objects are development/test uploads generated between July and August 2026.
- **DB Dependencies:** These objects map to ephemeral local/test database records that no longer exist or align with the production catalogue.

**Cleanup Plan:**
The `weprintit-assets` bucket is a legacy public bucket. Because it contains customer-derived previews, it must not be used for private customer data in production. We will abandon it entirely and provision two entirely new, structurally secure buckets: `firstmemoir-public` and `firstmemoir-private`.

## 4. Storage Provider Defense-in-Depth

The `r2.provider.ts` service has been hardened:
- `validateAndGetBucket` now rigidly maps `previews/*` to `env.R2_PRIVATE_BUCKET_NAME`.
- `getPublicUrl` actively refuses to generate URLs for `previews/*` or `customers/*`, throwing a `Forbidden` error if accidentally invoked by an upstream controller.

## 5. Upload Security Path

The core upload lifecycle endpoints have been re-audited and confirmed secure:
- `POST /upload-url`: Protected by `ensureCartSession`. Defines strict MIME type (WebP, JPEG, PNG, HEIC) and size limits (15MB private, 5MB public).
- `POST /upload-complete`: Re-verifies R2 object existence and size against the private threshold. Generates the preview securely.
- `GET /read-url` / `GET /preview/*`: Enforce strict ownership checks (`session_id` match OR `user_id` match OR `ADMIN` role).

## 6. Razorpay Status Semantics

Idempotency and state synchronization have been verified against the Razorpay API:
- `created`: Order is fresh.
- `attempted`: The user opened checkout but failed/abandoned. The system gracefully marks the local order `EXPIRED` and re-initializes a new Razorpay order ID to prevent stale cart deadlocks.
- `paid`: Local webhook handlers atomically transition the order to `CONFIRMED`. Re-initialization rejects with HTTP 409, preventing double-payments.

## 7. Staging Configuration Consistency

Repository-wide search confirmed the eradication of legacy single-bucket configurations.
- Replaced `R2_BUCKET_NAME` with `R2_PUBLIC_BUCKET_NAME` and `R2_PRIVATE_BUCKET_NAME` in `render.yaml` and `.env.example`.
- `R2_PUBLIC_URL` is retained exclusively for `products/*`.
